# Проектирование базы данных (3NF) и ER-диаграмма

Решение выполнено на Python с использованием встроенной СУБД SQLite. Программа создаёт базу данных партнёров и отгрузок, позволяет просматривать и изменять данные партнёров, выводить историю отгрузок и формировать ER-диаграмму в PDF.

## Состав решения

- `main.py` — схема БД, демонстрационные данные, пользовательские команды и генератор ER-диаграммы;
- `test_main.py` — автоматические тесты ограничений целостности и основных операций;
- `requirements.txt` — зависимость для формирования PDF;
- `output/pdf/er_diagram.pdf` — готовая ER-диаграмма;
- `practice.db` — готовая база SQLite с внесёнными демонстрационными данными.

## Вводные данные

Для проверки работы самостоятельно подготовлен вымышленный набор данных:

- 6 партнёров из разных городов России;
- 8 товаров сетевого и серверного оборудования;
- 10 отгрузок за июль-сентябрь 2026 года;
- 18 товарных позиций в отгрузках;
- использованы статусы `planned`, `shipped`, `delivered` и `cancelled`.

Все названия организаций, реквизиты, адреса и контакты являются демонстрационными. Домены Email используют зарезервированную зону `.example` и не принадлежат реальным адресатам.

## Запуск

Требуется Python 3.10 или новее.

```bash
python3 -m pip install -r requirements.txt
python3 main.py demo
```

Отдельные команды:

```bash
# Повторное создание структуры и добавление демоданных
python3 main.py init --seed

# Просмотр партнёров
python3 main.py partners

# Редактирование данных партнёра
python3 main.py update-partner 1 --email new-address@example.com --phone "+7 999 123-45-67"

# История отгрузок выбранного партнёра
python3 main.py history 1

# Повторное формирование ER-диаграммы
python3 main.py diagram

# Запуск тестов
python3 -m unittest -v
```

## Сущности и связи

1. `partners` — данные партнёров. ИНН и Email обязательны и уникальны.
2. `products` — справочник товаров. Артикул `sku` обязателен и уникален.
3. `deliveries` — отгрузки. Каждая отгрузка относится к одному партнёру.
4. `delivery_items` — позиции отгрузки. Таблица разрешает связь «многие ко многим» между отгрузками и товарами.

Связи:

- `partners 1:N deliveries`;
- `deliveries 1:N delivery_items`;
- `products 1:N delivery_items`.

## Обоснование третьей нормальной формы

- В каждой таблице хранятся данные только одной предметной сущности.
- Значения полей атомарны, повторяющихся групп нет — соблюдается 1НФ.
- В `delivery_items` поля `quantity` и `unit_price` зависят от полного составного ключа `(delivery_id, product_id)` — соблюдается 2НФ.
- Неключевые поля не зависят друг от друга: реквизиты партнёра находятся только в `partners`, сведения о товаре — только в `products`, сведения об отгрузке — только в `deliveries`. Транзитивные зависимости отсутствуют — соблюдается 3НФ.
- Стоимость позиции не хранится отдельно, а вычисляется в представлении `partner_delivery_history` как `quantity * unit_price`, поэтому не возникает избыточность вычисляемых данных.

## Ограничения целостности

- `PRIMARY KEY` задан для всех таблиц;
- `FOREIGN KEY` связывает отгрузки с партнёрами, а позиции — с отгрузками и товарами;
- `NOT NULL` запрещает отсутствие обязательных значений;
- `UNIQUE` защищает ИНН, Email, артикул и номер отгрузки от дублирования;
- `CHECK` проверяет формат ИНН, положительное количество, неотрицательные цены и допустимый статус отгрузки;
- каскадное удаление применяется только к позициям удаляемой отгрузки, а удаление используемого партнёра или товара запрещено.
